# lamp_detection_example

Демо-приложение пакета [`lamp_detection`](../README.md). Показывает весь пайплайн на
реальном железе: превью камеры, перетаскиваемые ROI, калибровку в три состояния,
Live-детекция двух сигнальных ламп и журнал событий со статусами доставки. Живые
числа смотрят потоком `LAMPDBG` в logcat и в покадровой CSV — экранов
«Расшифровка чисел» и «Диагностика» больше нет, они были нужны разработчику, а не
оператору у лампы (ЖУРНАЛ §6.20). По умолчанию работает
**живой отсчёт** (`liveReference: true`): вспышка = подъём доли над «полом»
своей рамки, калибровка не обязательна. Чтобы вернуться к модели эталонов,
`LampConfig(liveReference: false)`.

Приложение использует **только публичный API** пакета — импортируется
`package:lamp_detection/lamp_detection.dart`, `src/**` не трогается.

## Запуск

```
cd example
flutter pub get
flutter run
```

Пакет подключается по относительному пути (`lamp_detection: path: ../` в
`example/pubspec.yaml`), так что в `pubspec.yaml` пакета ничего менять не нужно.

## Разрешения

Уже прописаны в `example/`, ничего добавлять не требуется.

**Android** — `android/app/src/main/AndroidManifest.xml`:

```xml
<uses-permission android:name="android.permission.CAMERA"/>
<uses-feature android:name="android.hardware.camera" android:required="true"/>
```

**iOS** — `ios/Runner/Info.plist`:

```xml
<key>NSCameraUsageDescription</key>
<string>Камера нужна, чтобы видеть сигнальные лампы белой и красной и считать попадания.</string>
```

Плагин `camera` сам запрашивает разрешение при первом `CameraController.initialize()`;
если пользователь отказал, `session.errors` получит сообщение, приложение не упадёт.

## Что на экране

Сверху вниз:

1. **Кнопка `Пуск` / `Стоп`** (камера стартует сама при открытии экрана).
2. **Три кнопки калибровки** (`_CalibrationSteps`): `1 ФОН`, `2 БЕЛАЯ`,
   `3 КРАСНАЯ` — по одной на состояние стенда (`фон` → `белая горит` →
   `красная горит`, по `LampConfig.calibrationFrames` кадров на шаг). Нажатая
   кнопка **сразу начинает набор своего шага**: ни таймеров, ни обратного
   отсчёта, ни ожидания «детектор сам увидит лампу». Порядок нажатий не важен,
   переснять можно одну кнопку (недостающие состояния подставляются из рабочей
   калибровки). Кнопка показывает состояние своего шага: `N/M` — набирается,
   `✓` — принято, `⚠` — отвергнут, пустой кружок — ещё не снят. Под кнопками —
   одна строка: красная причина отказа либо `calibrationHint` из сессии
   («Погаси обе лампы и жми «1 ФОН»», «Включи белую и жми «2 БЕЛАЯ»», «Держи
   красную горящей»). Третьей кнопки, `Найти лампы`, больше нет: автопоиск
   удалён 19.11.2026 вместе с `LampLocator`, рамки наводятся только пальцем.
3. Поверх превью во время набора — `_CollectionOverlay`: `2/3 · ДЕРЖИ БЕЛУЮ`,
   крупное число оставшихся кадров (а во время стабилизации — `…` и
   `стабилизация · N с`), и янтарное предупреждение «Экспозиция не заперта» /
   «Пересвет». Живых кнопок здесь нет, поэтому касаний оверлей не перехватывает
   вовсе: рамки можно править прямо во время набора.
4. **Меню ⋮** — ровно пять пунктов, всё остальное из него убрано: `Решение:
   цвет (прежнее) / ЯРКОСТЬ + геометрия` (переключает `spatialVectors` на лету и
   сохраняет конфиг), `Сброс калибровки`, `Сравнить способы (OpenCV)` (тень —
   второй измеритель света, см. ниже), `Журнал событий`, `Ошибки`. CSV и
   поток `LAMPDBG` включены всегда и без переключателей (`_bootstrap`). Нет
   больше `Дамп кадра` (PPM в `databases/`), `Поворот ROI 90°`, `Новая сессия`,
   `Сравнить способы по CSV`, `Лог чисел`, `Сеть вкл/выкл`.
5. **Превью + `RoiEditor`** — два прямоугольника (WHITE / RED). Рамку можно
   схватить не только внутри, но и в ~24 px вокруг неё: это невидимая зона
   захвата, которая не залезает на вторую рамку и не выходит за край превью.
   Кружок на углу меняет размер, двойной тап — увеличить, долгое нажатие —
   уменьшить. Первый delta считается от точки касания, поэтому рамка не
   отстаёт от пальца на первые 18 px. Координаты нормализованы, ROI переживают
   поворот и смену разрешения. **Отпускание пальца сразу пишет ROI в
   `SettingsStore`** — раньше сохранение происходило только по тапу, и наводка
   терялась при перезапуске приложения.
6. **Полоса `ГОТОВ К РАБОТЕ`** (`_ReadyBanner`) — единственный ответ на вопрос
   «можно ли уже считать». Пока нельзя — там же написано чего не хватает: камера
   не пущена, кадра ещё нет, идёт набор шага, нет калибровки, «свет
   стабилизируется, осталось N кадров». Висеть на «Запуск…» экран не вправе
   вовсе: подъём камеры ограничен 25 с и заканчивается внятной подсказкой.
   Справа от полосы — кнопка `СВЕТ ЗАНОВО` (`session.relearnLight`): сбрасывает
   «пол» живого отсчёта, гистерезис и состояние «горит», не трогая счётчики.
   Нужна она затем, что рамки наводят ПОСЛЕ «Пуска» — окно «пола» к этому
   моменту уже снято с фона и с чужого места кадра (то же делает и любое
   движение рамки); жать её надо при погашенных лампах.
7. **Строка состояния** — две плашки `БЕЛАЯ` / `КРАСНАЯ` со счётчиками (загораются
   в такт `LampEvaluation.whiteLit` / `redLit`) и кнопка `↺` — сброс счётчиков
   без смены сессии. Под ней — одна серая строка `_message`: только следующее
   действие и ничего больше («Наведи рамки», «Жми «1 ФОН»», «Набор «фон»…»,
   отчёт шага, `БЕЛАЯ #12`). Полных исключений, UUID и путей здесь нет — они в
   «Ошибках».
8. **Из меню** — `Журнал событий` (все `HitEvent` текущей сессии + статус
   доставки из SQLite: `pending` / `sent` / `failed xN`) и `Ошибки` (последние 50
   сообщений из `session.errors`).

## Типовой сценарий проверки

Со стендом (`sim_app/` — табло с лампами на втором экране):

1. Закрепить телефон так, чтобы обе лампы попали в кадр (штатив, подставка).
2. Камера стартует сама → дождаться превью (кнопка `Пуск` нужна только после
   остановки).
3. Потянуть рамки WHITE и RED точно на колпаки. Рамка сохраняется в настройках в
   момент отпускания пальца — ничего отдельно нажимать не нужно.
4. Три состояния — три нажатия, в своём темпе и в любом порядке: погасить обе
   лампы → `1 ФОН` (идёт набор, держать, пока счётчик не дойдёт до нуля) →
   включить белую → `2 БЕЛАЯ` → погасить белую, включить красную → `3 КРАСНАЯ`.
   Кнопка стартует набор **сразу**, как её нажали: никаких фаз ожидания и
   никаких секунд, которые нужно угадать. Если шаг отвергнут (`⚠` на его кнопке
   и причина в строке под кнопками) — переснять **только его**, остальные состояния
   останутся. Пока не снят `1 ФОН`, кнопки лампы набор не начинают — отвечают
   «начни с «1 ФОН»», потому что отклик лампы не от чего мерить.
   **Двинуть рамку после калибровки = потерять калибровку**: с 20.11.2026
   сессия сама сбрасывает её и пишет «Рамки сдвинулись — калибровка сброшена»,
   потому что фон и эталоны были измерены по другим пикселям. И рамки не должны
   перекрываться: на стенде 20.11 красная (`x 0.000–0.635`) накрывала белую
   целиком, и всё, что давала красная лампа, читалось как фон (`Y r=48`,
   `rf=0.000`). Проверить наводку можно с кабеля:
   `adb shell "run-as dev.lampdetection.lamp_detection_example cat shared_prefs/FlutterSharedPreferences.xml"`.
5. Сброс счётчиков (`↺`), затем прогон панели. Счётчик табло — эталон, у него
   своя независимая статистика.
6. Сверить: `БЕЛАЯ` / `КРАСНАЯ` в «Журнале» и номера событий против эталона.
   Расхождение разбирается по CSV + `PANEL`-строкам лога, а не на глаз.
7. CSV пишется сама, ничего включать не нужно. Забрать файл из каталога: `adb
   shell run-as dev.lampdetection.lamp_detection_example ls databases`, затем
   `adb exec-out run-as … cat databases/<file>.csv`, и прогнать через
   `DetectionSession.replayCsv` — он восстановит три состояния из колонок
   `calibration_step` и посчитает события без камеры.

Если рамки наведены верно, а `aW`/`aR` нулевые — почти наверняка виновата
ориентация кадра: смотреть строку `LAMPROI turns= mirror=` (печатается при каждом
шаге калибровки) и сравнивать координаты рамок экрана с координатами кадра.
Подробнее — `../docs/ЖУРНАЛ.md` §6.1.

## Второй способ мерить свет (OpenCV)

Важно понять, что это **не режим детекции**. Рабочее решение всегда принимает
обычный конвейер; OpenCV подключается к сессии единственным возможным способом —
как `ShadowProbe`: получает тот же сырой кадр, те же рамки и уже принятое решение,
вызывается последним шагом после отправки событий и не имеет канала обратно. Он
может только назвать числа — создать или отменить событие нечем физически
(в библиотеке это закреплено тестом).

Как включить и где смотреть:

1. Меню `⋮` → `Сравнить способы (OpenCV)`. Пока тень включена, этот же пункт
   показывает `Отчёт OpenCV (N кадров)` — по нему видно, что измерение идёт.
2. Прогнать сцену табло как обычно (`off → белая → off → красная`). В строке
   состояния — `OpenCV считаю…`.
3. Меню `⋮` → `Отчёт OpenCV (N кадров)` — тень выключается, и результат сразу в
   трёх местах: **диалог** `Сравнение способов (OpenCV)` (только сводка
   расхождений и `центр − кольцо`: таблицу в 14 колонок с телефона не читают),
   **logcat** (`adb logcat -d | Select-String "OPENCV"`) и **файл**
   `databases/lamp_opencv_compare.txt` рядом с CSV:
   `adb exec-out run-as dev.lampdetection.lamp_detection_example cat databases/lamp_opencv_compare.txt`.

Смотреть надо одну колонку: `|рабочий − OpenCV|`. На стенде (20.11.2026, 105
кадров, 40 пар) она была в пределах ~0.1 единицы по всем величинам, а `центр −
кольцо` совпало до десятой (77.0 | 77.0) — то есть оба способа мерят одно и то же,
и спорить о том, кто прав, бессмысленно: смысл имеет только решение автомата.

Три ограничения, о которых стоит помнить заранее:

- **Сборка после добавления `opencv_dart` идёт ~20 минут и молчит.** Хук `dartcv4`
  не скачивает пребилд, а кросс-компилирует OpenCV NDK-ом под arm64-v8a; в
  консоли за это время не появляется ничего, и `flutter run` выглядит как
  зависшее приложение (это одна из реальных причин жалобы «зависло на старте»).
  Кэш сборки лежит в `.dart_tool/hooks_runner/shared/dartcv4`, поэтому `flutter
  clean` и `flutter pub get` возвращают те же 20 минут. **Вторую сборку, пока
  первая не закончена, не запускают**: она отждёт 5 минут и упадёт с `Could not
  acquire the lock to …dartcv4\.lock`.
- Пока тень включена, каждый кадр проходит пиксели **дважды** — частота
  обработки падает. На счёт это не влияет (решение принято до тени), но
  сравнивать тайминги прогона нужно с выключенной тенью.
- Если нативная часть OpenCV на устройстве не поднялась, прогон не падает:
  сессия ловит ошибку, пишет в `Ошибки` `Теневой измеритель отключён: …` и
  продолжает считать одним способом. В отчёте тогда `сбоев N` равное числу
  кадров — это не «способы разошлись», это измеритель не работал.

## Где что лежит

```
example/lib/
├── main.dart                        // MaterialApp, тёмная тема
├── home_page.dart                   // DetectionSession + UI, кнопки, readiness-полоса, LAMPDBG/LAMPROI
├── opencv_features.dart             // тот же кадр, измеренный OpenCV (`opencv_dart`)
├── opencv_shadow.dart               // `OpenCvShadowInstrument`: накопление пар и текст отчёта
└── widgets/
    ├── roi_editor.dart              // перетаскиваемые ROI поверх превью
    └── event_log.dart               // журнал + статусы доставки
```

`home_page.dart` — единственная точка, где собирается `DetectionSession`:
источник кадров, репозиторий, отправитель, настройки, CSV-рекордер. Всё остальное
получает готовую сессию через конструктор.

Значение каждого числа на этих экранах, формулы и где что ещё посмотреть —
[`../docs/КАРТА.md`](../docs/КАРТА.md) (§5–§6).

## Замечания по железу

- **`ResolutionPreset.medium` (720×480)** по умолчанию: ROI это позволяет, и анализ
  кадра успевает между 30 fps. Если `avgAnalysisMs > 8` (`session.diagnostics`)
  — поднимите `subsampleStep` (по умолчанию 2; например, до 3–4) или уменьшите
  ROI.
- **Реальная частота обработки кадров ниже частоты камеры**: при `_busy` кадр
  пропускается. Смотрите `cameraFps` / `analysisFps` / `droppedFrames` — от них
  зависит, успеет ли короткая вспышка набрать `onConfirmFrames`.
- **Автоэкспозиция** на части телефонов продолжает жить после `lockSettle`:
  смотреть `exp=lock/auto` в `LAMPDBG live` (и `sensorExposureTimeNs` /
  `sensorSensitivity` в CSV). Если они дрейфуют, уходят вверх и доли пикселей, и
  амплитуды — без всякой вспышки.
- **Панорамирование рукой** во время калибровки сдвигает baseline. Калибруйте только
  когда телефон зафиксирован.
- **Пересобирать на телефон только через `adb install -r -d`**: `flutter install`
  сначала удаляет приложение и стирает SharedPreferences — вместе с рамками и
  калибровкой.

```powershell
cd example
flutter build apk --debug
adb install -r -d build\app\outputs\flutter-apk\app-debug.apk
adb shell monkey -p dev.lampdetection.lamp_detection_example -c android.intent.category.LAUNCHER 1
```
