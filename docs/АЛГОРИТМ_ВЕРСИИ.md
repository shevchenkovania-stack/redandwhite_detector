# Версии алгоритма детекции и текущая спецификация

Файл отвечает на один вопрос: **по какой версии алгоритма код работает сейчас, а по
какой должен работать**. Читается сверху вниз: таблица версий → дословная
спецификация v6 → она же словами для человека → что уже есть в коде → чего нет.

## 1. Как устроено версионирование

- Версия алгоритма — это **способ решения** (какие признаки, откуда порог, как
  подтверждается событие), а не номер сборки и не формат CSV.
- Формат диагностики живёт отдельно: CSV в формате **v6** (91 колонка; у прежнего
  v5 — 69), причём прежние строки читаются и остаются — новых колонок добавлено
  ровно 22, ничего из прежних не сдвинулось.
- Каждая принятая версия отмечается в `docs/ЖУРНАЛ.md` (§2 и §3) и в
  `CHANGELOG.md`, а зафиксированное состояние кода — git-тегом.
- Код, написанный по прежней версии, не удаляется молча: он остаётся рабочим
  режимом, пока новый не измерен на тех же записях.

## 3. Спецификация v6 (дословно, получена 26.11.2026)

```
OBJECTIVE

Develop a computer vision system that detects and counts confirmed
ON events for two signal lamps: WHITE and RED.

The system must distinguish direct lamp activation from reflected light
caused by the neighboring lamp.

MODES

Implement exactly two modes:
1. HSV
2. HSV_CALIBRATION

No YOLO or neural networks.
No additional detection modes.


1. ROI SETUP

User manually selects:

ROI_WHITE
ROI_RED

ROIs must cover the lamp's emitting surface as accurately as possible.

Do not include excessive surrounding objects.

Analyze spatial distribution of light inside each ROI.
Do not use a single maximum brightness pixel as a detection criterion.


2. FRAME PROCESSING

For each captured frame:

- Convert image to HSV.
- Extract WHITE ROI.
- Extract RED ROI.
- Calculate features independently for both ROIs.

Features:

- Median V
- Median S
- Hue distribution
- Bright pixel ratio
- Color pixel ratio
- Bright pixel spatial distribution
- Spatial brightness distribution across ROI
- Bright core intensity
- Bright core area
- Connected bright regions
- Temporal stability
- Feature change relative to OFF profile

Use a combination of features.
Do not rely on a single threshold or individual pixels.


3. WHITE DETECTOR

Evaluate:

- Brightness increase
- Bright pixel ratio
- Neutral-light color characteristics
- Saturation distribution
- Spatial brightness pattern
- Bright core presence and intensity
- Similarity to calibrated WHITE_ON profile, when calibration is enabled

Do not require pure white HSV values.
Allow warm-white and camera-dependent color variations.


4. RED DETECTOR

Evaluate:

- Red Hue ranges, including HSV wraparound
- Saturation
- Brightness
- Red pixel ratio
- Spatial brightness pattern
- Bright core presence and intensity
- Similarity to calibrated RED_ON profile, when calibration is enabled

Red Hue alone must never confirm activation.


5. REFLECTION REJECTION

When one lamp activates, its light may affect the neighboring ROI.

Do not classify the neighboring lamp as ON merely because:
- Brightness increased
- Red pixels appeared
- Saturation increased

Evaluate the spatial distribution of the light.

Compare:
- Central emitting region
- Remaining lamp ROI
- Bright core
- Bright area ratio
- Spatial intensity distribution
- Calibrated ON profile
- Calibrated OFF profile
- Neighbor-lamp activation influence

A true lamp activation should match the characteristic emitting pattern
of the lamp, not merely a general illumination change.

Use the calibration data to characterize how WHITE activation affects RED ROI,
and how RED activation affects WHITE ROI.

If the signal cannot be confidently distinguished from reflected light,
do not confirm the neighboring lamp as ON.

Note:
If reflected light produces a pixel pattern indistinguishable from direct
lamp activation, vision-only detection cannot reliably separate the two.


6. HSV MODE

Use predefined HSV detection rules.

WHITE:
- Brightness
- Neutral-light characteristics
- Bright pixel ratio
- Spatial distribution
- Temporal confirmation

RED:
- Red Hue
- Saturation
- Brightness
- Red pixel ratio
- Spatial distribution
- Temporal confirmation

Apply hysteresis and temporal confirmation.

Do not count uncertain events.


7. HSV CALIBRATION MODE

CALIBRATION STEP 1 — BOTH LAMPS OFF

Collect stable frames.

Create:
WHITE_OFF_PROFILE
RED_OFF_PROFILE

Store robust statistics for all extracted features.

Reject unstable frames and outliers.

CALIBRATION STEP 2 — WHITE ON, RED OFF

Collect stable WHITE ON frames.

Create:
WHITE_ON_PROFILE

Simultaneously record the observed influence of WHITE activation
on the RED ROI.

Create:
RED_ROI_WHITE_SPILL_PROFILE

CALIBRATION STEP 3 — WHITE OFF, RED ON

Collect stable RED ON frames.

Create:
RED_ON_PROFILE

Simultaneously record the observed influence of RED activation
on the WHITE ROI.

Create:
WHITE_ROI_RED_SPILL_PROFILE

CALIBRATION STEP 4 — BOTH ON (OPTIONAL)

If simultaneous activation is possible in production,
collect stable frames with both lamps ON.

Create:
BOTH_ON_PROFILE

Do not require this step if simultaneous activation is impossible.

Reject transition frames, camera movement, unstable exposure,
and noisy measurements.


8. PROFILE STORAGE

Store feature distributions rather than single values.

Profiles:

WHITE_OFF_PROFILE
WHITE_ON_PROFILE

RED_OFF_PROFILE
RED_ON_PROFILE

RED_ROI_WHITE_SPILL_PROFILE
WHITE_ROI_RED_SPILL_PROFILE

BOTH_ON_PROFILE (optional)

Use median and robust percentile ranges.

Do not use raw min/max as the only profile boundaries.

Calibration profiles must be validated before runtime.


9. RUNTIME DETECTION

For each frame:

1. Extract features for WHITE ROI.
2. Extract features for RED ROI.
3. Evaluate WHITE activation.
4. Evaluate RED activation.
5. Evaluate possible neighboring-lamp reflection.
6. Compare current features with OFF, ON and spill profiles
   when calibration mode is enabled.
7. Determine independent confidence for WHITE and RED.
8. Apply temporal confirmation.
9. Apply hysteresis.
10. Update lamp state machines.
11. Count confirmed OFF -> ON transitions.
12. Record diagnostics.


10. STATE MACHINE

Each lamp operates independently.

States:
UNKNOWN
OFF
ON

Use separate ON and OFF thresholds.

ON threshold must be higher than OFF threshold.

Require temporal confirmation for state transitions.

UNKNOWN -> OFF:
Confirm stable OFF evidence.
Do not increment the counter.

UNKNOWN -> ON:
Confirm ON evidence.
Do not count initial state as a new event.

OFF -> ON:
Confirm activation.
Increment the corresponding counter exactly once.

ON -> OFF:
Confirm deactivation.
Do not increment the counter.

ON -> ON:
Do not count again.

OFF -> OFF:
No action.

Uncertain state:
Do not count.
Do not force a transition.


11. COUNTING

WHITE_COUNT increments only on confirmed WHITE OFF -> ON.

RED_COUNT increments only on confirmed RED OFF -> ON.

Each activation must produce exactly one count.

Prevent repeated counting while a lamp remains ON.

A confirmed OFF transition is required before the next activation
can be counted.


12. BACKGROUND

Do not implement a separate background ROI or adaptive background
learning in the initial version.

Use lamp ROIs, OFF profiles, ON profiles, spatial features,
neighbor-spill calibration, hysteresis and temporal confirmation.

Background analysis may be added later if validation demonstrates
that it is necessary.


13. DIAGNOSTICS

For each frame record:

- Timestamp
- WHITE features
- RED features
- WHITE state
- RED state
- WHITE confidence
- RED confidence
- Candidate transition
- Reflection suspicion
- Confirmed transition
- Count event

Provide a way to inspect diagnostic values during testing.


14. VALIDATION

Test with:

- WHITE ON, RED OFF
- RED ON, WHITE OFF
- Both OFF
- Both ON if applicable
- RED light reflecting onto WHITE ROI
- WHITE light reflecting onto RED ROI
- Changes in ambient lighting
- Camera exposure changes
- Different camera-to-lamp distances
- Camera movement
- Different lamp brightness
- Short activation durations
- Glare and reflections

Measure:

- False positive count
- Missed activations
- Count accuracy
- Detection latency
- Reflection rejection rate
- Stability during ambient lighting changes

Do not claim reliable production accuracy until tested
with representative production lamp footage.
```

## 4. Тот же алгоритм словами для человека (дословно)

1. **Задача.** Камера наблюдает две лампы: красную и белую. Пользователь вручную
   задаёт область каждой лампы. Программа должна определять включение каждой
   лампы независимо, даже когда свет от одной лампы отражается на соседней.
2. **Выбор областей.** Для каждой лампы пользователь задаёт ROI максимально
   точно по светящейся поверхности, не захватывая лишние окружающие объекты
   (`ROI_WHITE`, `ROI_RED`). Внутри каждой ROI анализируем распределение света,
   а не просто максимальную яркость одного пикселя. Две ROI **не имеют права
   пересекаться**: одна и та же строка пикселей в двух зонах означала бы, что
   вспышка одной лампы засчитана обеим. Код это не оставляет на честное слово
   оператора: любая правка рамки проходит через `RoiLayout.separated`, который
   выталкивает её из-под соседней по оси наименьшего вторжения (касание краями
   законно), а кнопка «вплотную» (`RoiLayout.adjacent`) сближает пару до
   просвета `adjacentGap` = 0,02 кадра, оставляя видимым, что зон ДВЕ.
   Наводка не считается измерением: пока палец ведёт рамку, кадры не
   анализируются (`setRoiAiming`), а по окончании жеста всё, что было набрано по
   ПРЕЖНИМ пикселям, сбрасывается ровно один раз (`commitRoi` →
   `_dropCalibrationOnRoiMove`) — калибровка, «пол» живого отсчёта и порог шума.
3. **Анализ кадра.** Каждый кадр преобразуется в HSV. Для каждой лампы
   вычисляем: долю ярких пикселей; медианную яркость V; долю пикселей,
   соответствующих её цвету; насыщенность S; распределение ярких пикселей
   внутри ROI; изменение этих признаков относительно выключенного состояния.
   Для белой лампы ищем яркое нейтральное свечение. Для красной — яркое
   свечение с красным оттенком и достаточной насыщенностью.
4. **Защита от отражения соседней лампы.** Это ключевое изменение алгоритма.
   Когда красная лампа включается, красный свет может попасть в ROI белой
   лампы. Поэтому недостаточно проверять, появился ли красный цвет или выросла
   ли яркость. Мы дополнительно проверяем: где именно появились яркие
   пиксели; образуют ли они выраженное яркое ядро источника; насколько сильно
   изменился центр светящейся поверхности; соответствует ли пространственное
   распределение реальному включению лампы, а не засветке; соответствует ли
   изменение профилю настоящего включения, полученному при калибровке.
   Основной признак — характер свечения внутри самой лампы, а не просто
   появление цвета в рамке. Если отражение визуально практически идентично
   настоящему включению и попадает в ту же область, программно гарантированно
   разделить эти события невозможно. Поэтому рамки необходимо располагать по
   реальным светящимся поверхностям максимально точно.
5. **Режим HSV.** Используются фиксированные правила. Белая: яркость +
   нейтральность цвета + доля светлых пикселей + пространственное
   распределение. Красная: яркость + красный Hue + Saturation + доля красных
   пикселей + пространственное распределение. Каждая лампа определяется
   независимо. При недостаточных признаках алгоритм не меняет состояние.
6. **Режим HSV с калибровкой.** Калибровка проходит в такой последовательности:
   1) обе лампы выключены — записать OFF-профили обеих ROI; 2) включить только
   белую — записать её ON-профиль и одновременно зафиксировать, как её свет
   влияет на красную ROI; 3) выключить белую; 4) включить только красную —
   записать её ON-профиль и одновременно зафиксировать, как её свет влияет на
   белую ROI; 5) если в реальной работе возможны одновременные включения обеих
   ламп — дополнительно калибровать состояние обеих ON. Так система узнаёт не
   только лампу в чистом состоянии, но и характер паразитного освещения
   соседней области. Калибровочных кнопок на экране четыре, но обязательных
   ровно три: `bothOn` («обе горят») записывает четвёртое состояние сцены в
   baseline и в отчёт, однако `ProfileDecider.verdict` читает только OFF / ON /
   spill, поэтому на счёт вспышек шаг 4 не влияет — он отвечает лишь на вопрос
   «измерена ли двойная засветка» (журнал §52, §57). Калибровочные кадры должны
   быть стабильными. Переходные кадры, движение камеры и скачки экспозиции не
   сохраняются в профили.
7. **Определение включения.** Каждая лампа имеет собственное состояние
   `UNKNOWN → OFF → ON`. Используются разные пороги для включения и
   выключения, чтобы состояние не переключалось из-за колебаний света.
   Переход подтверждается несколькими последовательными кадрами или временным
   условием. Счётчик увеличивается только один раз при подтверждённом переходе
   `OFF → ON`. Выключение возвращает лампу в OFF, но счёт не увеличивает.
8. **Фон.** В первой версии отдельную рамку фона и автоматическое обучение фона
   не используем. Причина: сначала проверяем, можно ли надёжно определять лампы
   по их собственным ROI, профилям и пространственному распределению света.
   Адаптивный фон добавит новые риски и усложнит отладку.

## 6. Порядок работ по v6: что сделано и что осталось

1. **Два режима вместо трёх.** Спецификация требует ровно `HSV` и
   `HSV_CALIBRATION`. Сейчас `LampCountMode = etalon | live | hsv` плюс флаг
   `hsvSignatureNaming`. Дешёвый шаг: оставить прежний код, наружу показать два
   режима (HSV = текущий hsv с вето, HSV_CALIBRATION = hsv + обязательная
   калибровка), etalon/live пометить deprecated и убрать из меню. Цена — тесты,
   которые явно просят прежние режимы, и `withCountMode`.
   **Сделано 26.11.2026:** наружу показываются ровно `LampCountMode.hsv` и
   `LampCountMode.hsvCalibration`; различает их ОДНО сохранённое число
   `v6ProfileDecision`, поэтому оба режима работают с одной и той же калибровкой
   и одной записью, а разница режимов — только в способе решения. Прежние
   `etalon`/`live` помечены deprecated и остались рабочими: тесты пришлось
   тронуть только там, где прежнего режима больше нет.
2. **Пространственные признаки ядра.** Нужно: площадь яркого ядра, его
   интенсивность, связные bright-области, «центр поверхности vs остальная ROI».
   В `FrameFeatures` есть только `p90Luma` (интенсивность proxy), `clippedRatio`
   и `lumaStdDev` — то есть **число** про распределение, но не его **геометрия**.
   Это самая дорогая часть: новый проход по пикселям в `FeatureExtractor` и
   новые колонки CSV (формат v6).
   **Сделано:** `FeatureExtractor._scan` считает геометрию света тем же циклом по
   опрошенным пикселям (`brightFrac`, `coreAreaFrac`, `coreIntensity`,
   `coreRegions` — связные области по сетке маски ядра, `coreCenterFrac`,
   `centerContrast`), а включается это одним флагом `v6Spatial` (по умолчанию
   включён: профиль обязан набираться теми же числами, которыми решение
   проверяется). Все 15 чисел — вектор `V6Feature`, он же
   `FrameFeatures.toVector()`, он же CSV v6.
3. **Медианные V/S и распределение оттенка.** Есть окна долей и перцентили
   яркости, нет медианы V, медианы S и гистограммы hue. Дёшево: те же
   поштучные счётчики, что уже считают `cool`/`warm`, расширить на медианы по
   карманам и 8–16 корзин оттенка (окружение 0°/360° — «wraparound» красный
   требует именно корзин, а не среднего).
   **Сделано:** `medianV` из 256 корзин V и `medianS` из 64 корзин S тем же
   `_percentile`, что и `p90Luma`; оттенок — 16 корзин (`hueBins`), и
   `hueRedFrac` берёт КРАЙНИЕ корзины (0 и 15), потому что красный на шкале
   0°/360° живёт с обеих сторон. Среднего оттенка в признаках нет.
4. **Spill-профили как отдельный объект.** Данные собираются (см. раздел 5), но
   сейчас из них выучивается одна граница именования (`HsvSignature`), а не
   «как белая включает красную ROI». Нужно: 7 профилей по списку v6,
   медиана + квартильные интервалы, и проверка на runtime по ним, а не по
   перевесу двух подъёмов.
   **Сделано:** `FeatureProfile` (`lib/src/models/feature_profile.dart`) —
   робастное распределение по каждому признаку (медиана, p05/p25/p75/p95,
   σ = IQR/1.349, нижняя граница разброса `v6MinSigma`), `LampProfiles`
   (`lib/src/detection/v6_profile.dart`) — шесть обязательных профилей,
   два spill-профиля и необязательный `BOTH_ON`. Spill собирается из ЧУЖОЙ зоны
   того же состояния, то есть «как белая заливает красную ROI» измеряется на
   шаге «белая горит», а не угадывается.
   * Важно про полномочия: `ProfileDecider` — только **вето на восходящем
     фронте**. Имя вспышки, падающий фронт, гистерезис и правило одной корзины
     остались на измеренном пути v5; вердикты считаются и при выключенном
     флаге отказа, чтобы одна запись сразу давала сравнение двух способов.
5. **Уверенность (confidence) по каждой лампе и «reflection suspicion» в
   логе.** Сейчас есть булево «выше порога» и `amb`/`both` счётчики. Нужно
   число 0..1 на лампу и колонки в CSV — иначе §13 невыполним: по записи
   должно быть видно, ПОЧЕМУ событие не подтвердилось.
   **Сделано:** `ProfileVerdict.confidence` и `.suspicion` (оба 0..1) лежат в
   `LampEvaluation`, печатаются в `LAMPDBG` как `prof cw=/cr= sw=/sr=` и пишутся
   в CSV (колонки 87…90). Причина отказа — строка `unknownReason`, счётчики
   `refusedFrames`/`reflectionRefusals`/`unknownFrames` (`rej=` и `unk=`).
6. **Состояние UNKNOWN явно.** Автомат начинается с OFF, неопределённость
   сегодня = «не считать», но не состояние. Формально v6 требует UNKNOWN с
   подтверждением и запретом на счёт первого состояния.
   **Сделано как признак кадра, а не как состояние автомата:**
   `LampEvaluation.unknown` ставится, когда подъём своего цвета был, но ни одна
   лампа им не подтверждена; почему — в `unknownReason`, сколько таких кадров —
   в `unknownFrames`. Счёт такой кадр не увеличивает, что и требует §STATE, но
   отдельного состояния у `HitStateMachine` нет, и переписывать автомат под
   состояние, которого на стенде не бывает, не стали.
7. **Шаг 4 калибровки «обе включены», опциональный.** Сейчас трёх шагов
   достаточно; четвёртый нужен только если одновременно горение бывает в
   производстве — и это ровно тот вопрос, который закрыт двусмысленно (см.
   пункт 9).
   **Сделано:** `CalibrationStep.bothOn` есть и помечен `isOptional` — мастер
   набора сам туда не ведёт, «готовность» калибровки от него не зависит; это
   отдельная кнопка, которая добавляет в собранную модель профиль `BOTH_ON`.
   Без него решение по профилям всё равно принимается: `canDecide` требует
   ровно шесть обязательных профилей.
   * Уточнение по факту (27.11.2026, журнал §57): профиль `BOTH_ON` в `verdict`
     не читается вовсе, то есть шаг 4 сегодня **на счёт не влияет**; поэтому из
     UI убрана и подпись «по желанию», и приглашение снять его после шага 3 —
     человеку хватает трёх нажатий.
8. **Метрики валидации, а не только «ошибки против разметки».** Из v6 §14
   сейчас меряется: ложные (+ лишние события), пропуски, точность счёта. Не
   меряется: **задержка обнаружения**, **rate отказа отражения**, **устойчивость
   при смене освещения зала**. Всё это считается по тому же CSV, нужен только
   разбор в `tools/hsv_decide.py`/`RunAnalyzer`, не новый съёмочный материал.
   **Сделано в Dart:** `RunAnalyzer.analyzeBothModes` разбирает одну запись двумя
   способами и отдаёт `RunAb` — разницу счётцов плюс **задержку** по каждой
   лампе (`RunLatency`: измеренная, пропущенная, лишняя); rate отказа отражения
   — это `refusedFrames`/`reflectionRefusals`, которые видно и в логе, и в CSV.
   **Не меряется:** устойчивость при смене освещения зала — под неё нет ни
   разметки, ни клипа, и выдуманное число здесь не поможет.
   * Python-эталон `tools/hsv_decide.py` остался способом v5: решения по
     профилям в нём нет. Значит v6 сверяется по CSV самого приложения
     (`RunAnalyzer`), а не по офлайн-разметчику, и «Dart ↔ python» по профилям
     в этом корпусе не получить.
9. **Расхождение с v6 §10 — решено заказчиком 26.11.2026 в пользу правила
   одной корзины.** §10 v6: «Each lamp operates independently». Мы 25.11.2026
   ввели жёсткое правило одной корзины (`LampDetector._oneBasket` — проигравший
   канал гасится принудительно) по слову «если ты считаешь белую, то не нужно
   класть в красную». Слово 26.11.2026: «правило оставь в v5, мне нравится как
   работает — не кидает одновременно и туда и сюда, такого не может быть на
   практике». Записано как решение, журнал 48.
   * Что это значит для переноса на v6: автоматы, состояния, пороги и
     подтверждение остаются независимыми (это §10 и есть), но **правило
     отнесения события к одной корзине не убирается** — оно часть продукта,
     а не часть способа счёта. Рефлексия соседней лампы обязана отсекать
     чужое включение **по признакам** (пространство + профили + spill), а
     `_oneBasket` остаётся последней страховкой, и по её счётчику (`both=`)
     видно, насколько часто признаки не справились;
   * проверка 11 (`test/hit_detection_test.dart`) переписана под правило —
     теперь она ждёт **одно** событие и зелёная; то же написано в документе
     `HitStateMachine`. Оба текста жили в противоречии с кодом с коммита
     `0f35fdf`, закрыто 26.11.2026;
   * открытый пункт 20 `docs/ЖУРНАЛ.md` этим закрыт.

По пункту 9 решение есть, и оно ограничивает перенос: пространственные
признаки и spill-профили делаются не для того, чтобы «разрешить два события»,
а для того, чтобы `both=` не рос — то есть чтобы проигравший канал отсекался
до страховки, а не после неё.

Отсюда остаток, без прикрас: ни одно число нового решения не измерено на стенде.
`v6MinConfidence 0.35` и `v6ReflectionVeto 0.65` — середина, выбранная до первого
прогона, и по умолчанию режим с профилями включён (`v6ProfileDecision = true`).
Если на прогоне `rej=` начнёт расти там, где события обязано быть, лечиться это
будет переключением на `HSV`, а не подкруткой порога вслепую. 60 ошибок приёмки
пока не пересчитаны: до ближайшего стенда v6 считается реализованной, но не
подтверждённой.

## 7. Приёмка v6 (чем проверяем, что «реализовано»)

Честный итог на 26.11.2026: каждый пункт ниже проверен тестом на синтетике
(`test/v6_profile_test.dart`, 29 проверок) и НЕ проверен на стендовом корпусе.
Реализовано — не значит принято.

* Тот же корпус записей и та же человеческая разметка, что меряли v5: цель — не
  превзойти 60 ошибок на `sign 0.06 3.0 auto manual`, а **не потерять** их при
  переходе на пространственные признаки (правило: новая схема обязана быть не
  хуже измеренного предыдущей сборки).
  * Чем это держится в коде сейчас: отказ профиля имеет власть **только
    отключать** подтверждение, а имя, падающий фронт, гистерезис и одна корзина
    считаются прежним измеренным путём, поэтому «не потерять» обеспечено самой
    схемой, а не обещанием. Сравнение двух способов на одной записи —
    `RunAnalyzer.analyzeBothModes` (`RunAb.whiteDelta/redDelta/eventDelta`).
  * Не сделано: сам пересчёт 60 ошибок — нужен прогон того же корпуса.
* Отдельной метрикой — отказ отражения: клипы, где белая заливает красную ROI и
  наоборот (`191142`, `191158`), обязаны давать ноль ложных событий соседней
  лампы.
  * Проверено тестом: на смоделированной засветке белый канал считает 0 событий
    вместо 1, `reflectionRefusals > 0`, а кадр остаётся с причиной «похоже на
    отражение соседней лампы»; своё включение при этом считается как считалось.
  * Не сделано: эти два клипа на новой схеме не прогонялись.
* Отдельной метрикой — задержка: от первого кадра подъёма до подтверждённого
  события, по тому же CSV.
  * Проверено тестом: `RunLatency` по каждой лампе, и в паре A/B видно, что
    отказ профиля платит пропуском (`profiled.whiteLatency.misses > 0`) —
    то есть метрика нужна именно за этим, а не для красоты.
* Ложные срабатывания на «только свет зала»: событий обязано быть ноль.
  * Не меряется без прогона: профиль по фону существует (`WHITE_OFF`/`RED_OFF`),
    но порога «зал не лампа» в коде нет и придумывать его нечем.
* Покадровая сверка Dart ↔ `tools/hsv_decide.py` по CSV живого прогона: расхождение
  по событиям означает, что реализация отъехала от офлайн-схемы, и чинится сразу.
  * По профилям эта сверка невозможна в принципе: python-эталон остался v5, и
    единственным судьёй нового способа пока остаётся CSV приложения.
